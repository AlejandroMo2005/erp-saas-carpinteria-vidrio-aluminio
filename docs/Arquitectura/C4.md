# Modelo C4 de Arquitectura

## 1. Propósito

Este documento describe la arquitectura de la plataforma ERP/SaaS mediante el modelo C4, utilizando los niveles de contexto, contenedores y componentes para representar las principales responsabilidades del sistema.

El modelo complementa la documentación de arquitectura existente y proporciona una referencia común para analizar límites, dependencias y responsabilidades.

---

## 2. Alcance

El modelo considera:

- Usuario de la plataforma.
- Frontend React/Vite.
- Backend Node.js/Express.
- MySQL.
- Redis.
- Servicios externos de IA.
- Integraciones externas relacionadas con facturación cuando correspondan.
- CI/CD como infraestructura de calidad y entrega.

Los diagramas representan la arquitectura lógica conocida del proyecto y no sustituyen la configuración real de despliegue.

---

## 4. Actores principales

### 4.1 Administrador

Gestiona configuración, usuarios y operaciones permitidas por su rol.

### 4.2 Vendedor

Realiza operaciones comerciales como clientes, proformas y pedidos según los permisos configurados.

### 4.3 Almacén

Gestiona operaciones relacionadas con materiales e inventario según los permisos correspondientes.

### 4.4 Cliente

Representa el rol de usuario cliente contemplado por el modelo de datos.

La autorización efectiva debe determinarse mediante el backend y no únicamente mediante restricciones visuales del frontend.

## 6. Frontend

El frontend utiliza React y Vite.

Sus responsabilidades principales incluyen:

- Presentación.
- Navegación.
- Formularios.
- Gestión del estado de interfaz.
- Consumo de API.
- Manejo de autenticación desde el navegador.
- Presentación de errores.
- Ejecución de flujos de usuario.
- Integración con funcionalidades de IA.

La comunicación con el backend se realiza mediante HTTP.

La configuración de API utiliza la variable `VITE_API_URL` cuando está definida y `/api` como valor utilizado por defecto en el cliente.

---

## 7. Backend

El backend utiliza Node.js y Express.

Sus responsabilidades principales incluyen:

- Exponer la API.
- Autenticar usuarios.
- Autorizar operaciones.
- Aplicar aislamiento por empresa.
- Validar entradas.
- Coordinar servicios.
- Acceder a repositorios.
- Gestionar transacciones.
- Aplicar reglas de negocio.
- Registrar eventos relevantes.
- Integrarse con MySQL y Redis.
- Coordinar integraciones externas.

La arquitectura actual utiliza una organización modular bajo `backend/src/modules` y componentes compartidos bajo `backend/src/shared`.

---

## 8. Base de datos MySQL

MySQL almacena la información persistente de la plataforma.

Entre las principales áreas de información se encuentran:

- Empresas.
- Usuarios.
- Sesiones.
- Clientes.
- Materiales.
- Variantes.
- Colores.
- Proveedores.
- Trabajos.
- Recetas.
- Proformas.
- Pedidos.
- Facturación.
- Auditoría.
- Solicitudes de materiales.
- Operaciones relacionadas con IA.

La estructura detallada se documenta en `docs/Base de Datos/`.

---

## 9. Redis

Redis participa en operaciones que requieren almacenamiento temporal o acceso rápido.

En el sistema se utiliza principalmente dentro de los mecanismos relacionados con:

- Revocación de tokens.
- Blacklist.
- Estado temporal de autenticación.
- Funciones que requieran almacenamiento temporal.

La responsabilidad exacta de cada uso debe mantenerse alineada con la implementación vigente.

---

## 10. Servicios externos

La plataforma puede comunicarse con servicios externos para funcionalidades específicas.

Entre ellos se encuentran proveedores de IA y servicios relacionados con procesos de facturación electrónica.

Las integraciones externas deben considerarse límites de confianza independientes.

El sistema debe controlar:

- Autenticación.
- Timeout.
- Errores HTTP.
- Cuotas.
- Respuestas inválidas.
- Disponibilidad.
- Registro de errores.

## 13. Autenticación

El flujo de autenticación puede representarse como:

```text
Usuario
   |
   v
Frontend
   |
   v
API de autenticación
   |
   +--> Validación
   |
   +--> Credenciales
   |
   +--> JWT / sesión
   |
   +--> Redis / blacklist
   |
   v
Acceso autenticado
```

El modelo actual contempla un `accessToken` administrado en memoria del cliente y un `refreshToken` mediante cookie `httpOnly`.

Los tokens y sesiones deben verificarse contra las reglas de expiración y revocación correspondientes.

---

## 14. Multi-tenancy

El aislamiento empresarial se basa en `empresa_id`.

Conceptualmente:

```text
Request
   |
   v
Autenticación
   |
   v
empresaId
   |
   v
Autorización
   |
   v
Repositorio
   |
   v
Datos de la empresa
```

Las consultas y operaciones que manejan información empresarial deben aplicar el contexto correspondiente.

El aislamiento debe comprobarse mediante pruebas positivas y negativas.

## 21. Seguridad como componente transversal

La seguridad no debe considerarse una única capa aislada.

Atraviesa:

```text
Frontend
   |
API
   |
Autenticación
   |
Autorización
   |
Servicios
   |
Repositorios
   |
MySQL / Redis
```

Los controles incluyen, según el flujo:

- Autenticación.
- Autorización.
- Multi-tenancy.
- Validación.
- CSRF.
- CORS.
- Cabeceras HTTP.
- Rate limiting.
- Gestión de sesiones.
- Auditoría.
- Logging.

- Identidad.

- Datos.

- Secretos.

---

## 25. Principios arquitectónicos

La arquitectura debe mantener los siguientes principios:

1. Separación de responsabilidades.
2. Validación en backend.
3. Autorización del lado servidor.
4. Aislamiento por empresa.
5. Persistencia consistente.
6. Uso controlado de servicios externos.
7. Observabilidad.
8. Pruebas automatizadas.
9. Evolución incremental.
10. Reducción progresiva de arquitectura legacy.

---

## 26. Arquitectura legacy

El proyecto mantiene evidencia histórica de una migración desde una estructura anterior hacia la arquitectura modular actual.

La existencia de archivos legacy debe considerarse deuda técnica hasta verificar:

1. Consumidores.
2. Dependencias.
3. Sustitución.
4. Pruebas.
5. Eliminación segura.

No debe eliminarse código únicamente por similitud nominal sin comprobar sus referencias.

---

## 27. Reglas para nuevas funcionalidades

Una nueva funcionalidad debe:

- Integrarse en el módulo correspondiente.
- Respetar las capas existentes.
- Reutilizar componentes compartidos.
- Aplicar validación.
- Aplicar autorización.
- Respetar multi-tenancy.
- Añadir pruebas apropiadas.
- Actualizar documentación relevante.
- Evitar duplicar arquitectura legacy.

## 29. Estado actual

El modelo C4 representa la arquitectura lógica conocida del proyecto.

La infraestructura de despliegue definitiva no debe inferirse de este documento.

Actualmente no se documenta Docker como mecanismo disponible de despliegue porque todavía no se ha establecido una configuración reproducible mediante Dockerfile y Compose.

Los detalles de producción deben actualizarse cuando exista una arquitectura de despliegue definida y verificable.

---

## 30. Mantenimiento

Este documento debe actualizarse cuando:

- Se agregue un contenedor.
- Se elimine un componente.
- Cambie la arquitectura modular.
- Cambie la persistencia.
- Se agregue una integración externa.
- Cambien los límites de confianza.
- Se modifique el mecanismo de autenticación.
- Se modifique el modelo multi-tenant.
- Se incorpore infraestructura de despliegue.

Los cambios arquitectónicos relevantes deben acompañarse de una decisión técnica cuando corresponda.
